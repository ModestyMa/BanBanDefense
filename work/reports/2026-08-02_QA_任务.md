## 三、BUG-004（本轮核心产出）

### 现象
真机冷启动 App，首页三卡（倒数日/番茄/记账）**随机停留在空状态**，且**不可自愈**。

典型失败态**自相矛盾**：宠物卡已显示「🔥 2 天／今天已打卡 ✓」（真实数据），同一屏记账卡却写「今天还没记账」——而当日实际已有 3 笔支出 -15.88。

### 复现率（实测硬数据）
**32 次冷启动，9 次失败，复现率 28%**

| 组 | 条件 | 失败 |
|---|---|---|
| N | kill 后 2s 重启 ×6 | 3/6 |
| O | 每轮附带清日志（时序被打散）×8 | 0/8 |
| A | kill 后 **2s** 重启 ×6 | 2/6（33%） |
| B | kill 后 **5s** 重启 ×6 | 2/6（33%） |
| R | ×5 | 1/5 |
| Q | ×1 | 1/1 |

**A/B 组失败率相同 → 与重启快慢无关**，不是「杀进程快速重启」的边缘场景，而是**普通冷启动即可触发**。

### 不可自愈（R 组实测）
失败态下：切倒数日 Tab → 切回首页 → **仍空**；再等 6 秒 → **仍空**。必须杀进程重启才有机会恢复。

### 根因（已定位到行）
1. `HomePage.ets:18` `private vm = homeVM` —— vm 为外部 `@ObservedV2` 单例，字段是 `@Trace`。`@Trace` 变化**只精确刷新 build 中直接读取该属性的 UI 节点**。
2. 宠物区（`:88/92/96/100/104`）是 `Text(this.vm.petEmoji)` 直接读取 → 依赖建立 → 刷新正常 ✅
3. 三卡（`:168/173/178`、`:186/188/190`）走 `countdownMain()`/`focusMain()`/`billMain()` 三个 **private 普通方法**（定义 `:30/41/49`）→ `@Trace` 在方法内部被间接读取 → **依赖未建立** → 不重算 ❌
4. 竞态：`aboutToAppear:24` 的 `vm.load()` 若在**首帧渲染前**完成则正常（72%），**首帧后**完成则三卡永久停在初值（28%）

### 排除项（避免主程序走弯路）
- 抓 hilog 全量日志，**无** `HomePage` 域「首页加载失败」error → `aboutToAppear` 的 `.catch` 未触发 → **`load()` 没抛异常、DB 数据完全正常**，非数据层问题
- `DatabaseHelper.get():94` 未初始化会 throw，且 `EntryAbility.onCreate:21` 的 `init()` 未 await、`onWindowStageCreate:58` 的 `loadContent` 不等 DB 就绪——属**并存隐患**，建议顺手加固，但**本 Bug 已排除该路径**

### 建议修法（QA 不改码，仅给方向）
把 `countdownMain()` / `focusMain()` / `billMain()` 改为 **`@Computed get` 计算属性**。同文件 `:17` 的 `@Computed get winWidthVp()` 就是现成正确写法，改动小、不动 VM、无需回归数据层。

### 扩散面
- ⚠️ 建议一并改：`PomodoroStatsPage.ets:15`（`private vm = pomodoroVM` + `weekDayNames()`/`maxWeekValue()`/`barHeightPercent()`，与 HomePage 完全同构）
- ✅ 已排除：`AccountReportPage` / `CountdownDetailPage` / `PomodoroTimerPage` 均为组件自身 `@Local`（整体重绘）。其中 PomodoroTimerPage 已真机实测倒计时正常跳动

### 定级理由
按 BUG_LIST 定义（P0=崩溃/数据丢失）本项数据未真丢，定 **P1**；但**首屏 + 28% 高频 + 用户感知等同「记的账不见了」+ 8/15 上架**，建议**按 P0 优先级插队**。
